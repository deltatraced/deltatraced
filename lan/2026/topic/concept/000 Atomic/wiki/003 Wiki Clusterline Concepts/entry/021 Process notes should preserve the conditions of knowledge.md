[[000 Term Process Note]]

The reason that [[001 Process notes should be immutable to act as an audit]] and [[006 Process notes are meant to be mined for evidence rather than linearly read]] is that they are not written to be reader-facing, they are written to allow a future reverse engineer to reconstruct the knowledge work that produces artifacts.

This means that we need process notes to host the key information considered that later is used to complete some objective. This could include key citations that changed our knowledge, mini experiments that taught us properties about our tools and systems, and assertions written at the time they are believed as well as why they are modified or invalidated written when this shift in belief occurs.

What have we considered? What did we try and fail? What mistakes have we made, and when did we realize, and why did we not realize prior?

This also includes memory aids, if we need to recall relevant information, resynthesize or explain it in a new context, this should be done in process notes as it is key knowledge work which is later utilized.

A lot of this is often missing from artifacts, such as source code. You may find glimpses in git commits, source code documentation, or communication channels, but process notes are meant to host this sort of knowledge work. 

One should also keep in mind that less is more: Try to be concise and include only the key decisive information needed. Trust that a future reverse engineer is able to synthesize that into the final artifact, given that sufficient context is provided.

This right here is an [[008 Term Artifact Note|artifact note]]. It is an explanation of a concept. A process note for this would maintain key conceptual changes and investigations about this very concept, and maintain how my beliefs about it change in time and why, as well as the origins that led me to creating this concept.
