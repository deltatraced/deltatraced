## 1.1 Some event sourcing architecture design

I also was working on designing table and event sourcing for chains of event tables.

![Pasted image 20250907120747.png](../../../../../../../attachments/Pasted%20image%2020250907120747.png)

The general idea is that table sourcing in events restores them with a full snapshot of a database table, but branch sourcing points to a specific event from a similar events table. This way we can have a notion of objects reset, where objects have a lifetime and their updates expire according to some rule but still maintain full history of system changes.

So in the drawing, obj 6 only exists for a limited period of time, once `branch source` is instructed again, it's erased from the final collection of objects as the event tape is executed.

Note that it is also possible to `seek` a previous version of events, which is similar to `branch source` except within the same table:

![Pasted image 20250907125942.png](../../../../../../../attachments/Pasted%20image%2020250907125942.png)

This complexity makes it non-trivial to decide how to fetch the latest state of objects in our system.

One solution is to follow a similar process to git, where besides the [git objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects) [DAG](https://en.wikipedia.org/wiki/Directed_acyclic_graph), there exists the current working directory. This corresponds to a software managed table with the current objects after applying all events.

Since this table is managed, we could include a metadata table describing the currently checked out version in the database.

For this, we may need database write notifications to update the virtual tables when new events are added.

Another solution is to make an interface that constructs a query that reads the objects at a specific version, or we create a SQL view.

So to conclude, let's capture some terms:

|term|meaning|
|----|-------|
|table source|An event that sets the state of all objects to the source table. An events table should either table or branch source, but not both.|
|branch source|Points to an event in another table to initialize the objects based off|
|seek|Go to a previous point within the event append-only store. Only for the same events table.|
|Event Lifetime|Often we may want to reset back to a snapshot. For example, if we had a `posts` table, we may have a `post_events` table that sources it, and a `post_drafts` table that branch sources the `post_events` table. Drafts are temporary, and may be discarded, but the posts events are more permentant. So even though they manage the same objects, they manage different lifetimes of objects.|
|virtual table|A table with contents that are autogenerated managed by software. The content may be erased and rebuilt often, so it is only used as a view.|
